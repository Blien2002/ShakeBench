# ShakeBench：IMU 辅助世界模型技术迁移方案

日期：2026-09-12
状态：B 场景迁移已完成，实体地基布局已通过场景预检及 39 项定向测试；完整世界模型迁移尚未完成。场景实现与验收范围见 [当前场景说明](world_fixed_arm_scene.md)。

本文整合以下要求：机械臂基座相对世界固定；仅保留一个刚性安装于工作台桌面下方的 IMU；模型输入为历史视频与 IMU，输出为未来物体视觉位置，再作为先验辅助其他 policy 学习；振动条件采用“Gamma × 振动模式”；项目代码、配置、测试与实施文档只保留最新设计，删除历史实现和兼容分支。

本文保留完整迁移路线。当前执行范围仅为阶段 B 及其必要的安装配置、上下文与审计变更；其余阶段不据此视为完成。

## 1. 迁移原则与目标边界

优先复用当前任务、物体、接触模型、隔振机构、传感器数值实现和成功判定。最小改动指复用仍适用的实现、减少重复代码，不以保留旧版本、双轨运行或兼容层来实现。

最终仅保留一条当前运行路线：

```text
振动模式 + Gamma + seed
          ↓
现有甲板驱动 → 隔振工作台 → 物体运动
                         ↓
                桌下唯一 IMU + 历史视频
                         ↓
                未来视觉位置预测器
                         ↓
                  预测先验 → policy
```

“机械臂固定”指基座相对世界坐标系固定，机械臂关节仍正常执行操作。“桌下 IMU 固定”指刚性安装在工作台上，随隔振工作台运动。

删除范围针对已被新设计替代的 ShakeBench 代码、配置、脚本、测试、实验输出和实施文档。仍被当前设计使用的 robosuite 基础能力、通用数值函数、物体资产与物理参数应保留，其实现年代不构成删除理由。无需通过重写 Git 提交历史完成本次工作区迁移。

## 2. 安装拓扑与机械臂位置

### 2.1 当前耦合与目标拓扑

迁移前环境通过 `DeckDriver.body_handles` 把 `robot0_base` 挂到甲板下，编译审计也要求机械臂是甲板的刚性子节点。B 阶段现已移除这项挂载，基座安装于与岸边连通的实体地基；甲板缩窄，工作台靠近地基侧，地基对应栏杆已留出开口。主要修改位置为 [vibration_pick_place_can.py](../robosuite/environments/manipulation/vibration_pick_place_can.py)。

新拓扑：

```text
world
├─ robot0_base                  世界固定，保留机械臂关节
├─ robot_support               独立固定支撑
├─ deck_driver                 沿用现有驱动
├─ deck                        沿用现有动态甲板
│  ├─ worktable                保留六自由度隔振机构
│  │  ├─ target_container
│  │  └─ table_imu_site         唯一 IMU 的安装参考
│  └─ 甲板视觉部件
├─ task_object                 保留 freejoint
└─ 固定外部相机
```

从甲板的 `body_handles` 和 `required_roles` 中移除 `robot_base`，让基座留在 `worldbody`。不为基座增加 mocap、锁定控制器、补偿力或额外自由度。现有甲板处理器已按角色工作，优先修改环境传入的角色集合，不重写整个驱动模块。

### 2.2 安装位置与支撑

迁移前几何中，基座位置为 `[-0.47, 0, 0.009]`，安装面位于甲板上。世界固定后继续占据原位置可能与运动甲板相交，不能仅修改父节点而不检查安装几何。

采用与岸边连通、下接坑底的实体地基，机械臂不带移动底座，直接刚性安装在地基顶面。地基与岸边同高、同材质；临坑三边的顶面沿用坑口黑色装饰包边，三面竖直内壁从地坪到坑底全部沿用原坑壁深黑色。岸边原包边与凸台包边在转角处完整搭接；对应区域的栏杆和坑壁段留出开口。工作台仍位于甲板靠近地基的一侧。当前尺寸、坐标、预览和验收范围见 [实体地基场景说明](world_fixed_arm_scene.md)。

以 `world_fixed_arm_v1` 表示当前唯一安装配置；复用现有场景资产，迁移所需配置后删除 `canonical`、`direct_mount_v1` 等旧安装选项及对应专属配置。不复制整套场景形成长期并存的版本，不增加 `legacy` 开关。

[scene_audit.py](../robosuite/models/arenas/scene_audit.py) 当前把机械臂安装面纳入甲板高度推导，需要改为分别检查“工作台支撑→甲板”和“机械臂支撑→世界”。删除旧的机械臂与甲板支撑接触豁免，增加新支撑与运动部件的间隙检查。

### 2.3 保持与重新验证的内容

保留甲板尺寸、工作台位置和尺寸、桌面材质、隔振器参数、目标容器、物体参数、接触模型和控制频率。

机械臂移出振动系统后，甲板承载与反作用力会变化。物理参数不变不意味着实际响应相同，因此必须重新检查甲板驱动误差、工作台响应和操作可达性。旧轨迹和旧通过结果不能直接沿用，不为追平旧响应额外添加配重。

## 3. 唯一桌下 IMU

### 3.1 复用传感器数值实现

[shakebench_sensors.py](../robosuite/utils/shakebench_sensors.py) 已支持任意刚体的安装位置、方向及杆臂加速度，采样、噪声、滤波和延迟实现可以继续使用。需要删除或改写 [shakebench_providers.py](../robosuite/utils/shakebench_providers.py) 中“基座上的零外参 IMU”假设。

| 项目 | 当前设计约定 |
|---|---|
| 数量与所属刚体 | 仅一个，所属刚体为 `worktable` |
| 安装位置 | 工作台局部坐标系中的桌面下方 |
| 外参 | 保留可校准的 XYZ 和安装方向 |
| 测量来源 | 工作台实际运动，加上安装点杆臂效应 |
| 采样率与噪声 | 起步保留现有 200 Hz、滤波、噪声、量化和单采样交付延迟 |
| 公共字段 | `table_imu_window`、`table_imu_dt_s`、采样时间戳 |
| 安装记录 | `sensor_parent=worktable`、安装外参、当前传感器配置身份 |

可用无质量的 `site` 表示桌下安装点，测量仍使用现有计算路径，避免同时维护两套 IMU 实现。安装位置按桌板厚度确定，不能用工作台质心冒充桌下安装点。

### 3.2 必须同步修改的语义

- 传感器序列化目前写死 `frame.parent=robot_base`，需改为工作台安装语义并重新生成配置 hash；删除旧字段和字段别名。
- 删除 `deck_imu_*` 公共接口以及机械臂基座、甲板 IMU 的构造选项。
- 删除固定 `deck_to_robot_base` 外参假设。保留固定的世界到机械臂基座变换和工作台到 IMU 变换；工作台到机械臂的关系随时间变化。
- 传感器创建、reset、物理步采样和交付不再由 V0–V3 层级决定。
- 静止时加速度计测量包含重力相关的比力及噪声，不能将“全零输出”作为静止验收标准。

旧 [V1 oracle](../robosuite/utils/shakebench_oracle.py) 把 IMU 当作甲板激励，再通过隔振传递模型估计工作台响应。桌下 IMU 已测到隔振后的运动，因此删除这段补偿及其专属参数、测试和文档，不通过重命名继续使用。

## 4. Gamma × 振动模式接口

### 4.1 统一构造入口

现有激励模块已具备确定性六轴谱线生成、频率缩放、轴选择、解析导数和 Gamma 标定。主要限制是 [build_band_table()](../robosuite/utils/shakebench_excitation.py) 的频带写死，以及部分 runner 只传入 Gamma、seed 和相位。

拟议接口：

```yaml
vibration:
  mode: multisine_v1
  gamma: 0.15
  seed: 42
  t0_s: 0.0
  mode_params:
    frequency_scale: 1.0
    active_axes: [tx, ty, tz, rx, ry, rz]
  gamma_definition: normal_peak_v1
```

所有环境入口、采集脚本和演示使用同一构造路径：

```text
模式参数 + seed + 相位
          ↓
单位强度 program
          ↓
按 Gamma 标定缩放
          ↓
现有 DeckDriver
```

模式决定波形、频谱、轴组合及轴间相对幅值，Gamma 决定统一标定后的整体强度。高层 `vibration` 配置与显式传入的 `deck_trajectory` / `excitation_program` 不能同时成为驱动来源，冲突时应报错。

优先在现有激励与标定模块中集中实现配置解析和 program 构造，避免多个 CLI 各自拼接配置。解析时校验未知模式、未知参数、非有限数值、负 Gamma、非法频率、非法轴及超出表示能力的谱线数量。

### 4.2 第一批模式与后续扩展

| 模式 | 最小实现 |
|---|---|
| `multisine_v1` | 把当前六轴多正弦作为最新接口中的一个正式模式 |
| `single_sine_v1` | 每个启用轴仅保留一个频率分量 |
| `custom_multisine_v1` | 开放各轴中心频率、带宽、相对幅值和谱线数量 |

保留现有多正弦是复用最新设计仍需要的波形能力，不保留它原先的独立运行路径、旧协议或旧兼容入口。

后续增加扫频、间歇振动等模式时，再扩展波形求值；统一返回 `q/qdot/qdd`，保持位移、速度、加速度相互一致，处理 ramp 和包络的导数。第一轮不建立插件系统或复杂继承结构。

### 4.3 Gamma 定义与标定

当前 [标定代码](../robosuite/utils/shakebench_calibration.py) 使用参考点的法向加速度峰值除以重力，并非直接将 Gamma 乘到六轴幅值。默认继续采用该物理定义，对每个模式、seed 和相位分别标定：

```text
level_scale = gamma_requested / gamma_unit(mode, params, seed, t0)
```

起步继续使用现有标定窗口，同时记录完整 episode 的峰值。不同模式不能各自使用未声明的窗口或归一化方式；后续加入持续时间更长的扫频、间歇模式时，应统一确定覆盖目标模式的标定窗口并记录协议身份。

纯水平平移在当前法向定义下可能始终得到 Gamma=0。接口应显式保留 `gamma_definition`：默认 `normal_peak_v1`；需要纯水平等模式时，可为整组实验统一启用参考点加速度模长定义。不能按模式自动切换定义，也不能将两种定义下相同数值当成相同条件。单位强度标定结果为零而请求正 Gamma 时必须报错。

`gamma=0` 应在所有模式下产生零激励。改变 Gamma 时保持模式参数、频率、相位与 seed 不变。Gamma 标定基于命令，不使用某个物体滑动结果或 policy 成功率反向定义强度。

运行记录至少包含：

```text
mode / mode_params / mode_version / gamma_definition
gamma_requested / level_scale / calibration_window
excitation_seed / t0 / program_hash
```

命令强度与实际甲板、工作台响应分别记录；不能把不同模式下相同 Gamma 解释为桌面运动、滑移风险或任务难度完全相同。

新模式继续使用原物理步长，逐模式检查频率、位移、转角及实际响应；原模式的有效强度范围不能自动覆盖新模式。新增 Gamma 定义也不能直接替代现有法向脱离、接触和位移等物理限制的检查量。

## 5. 视频与 IMU 观测、历史缓存和监督数据

### 5.1 当前观测路径

当前环境禁止 State 层级同时启用相机，而无 State 层级时又不会创建振动 provider。删除旧 V0–V3 累积观测制度，改为当前唯一的视觉学习观测合同，并将传感器采集与模型输入选择分开。

环境提供当前 RGB、当前已交付的桌下 IMU 数据与时间戳，以及 policy 必需的机器人自身状态。历史缓存放在一个薄 wrapper 中，通过现有环境当前观测构造视频块和 IMU 历史，模型推理不进入仿真核心。

模型输入白名单保持为历史视频和桌下 IMU；下游 policy 所需的机器人自身状态通过单独的 policy 接口提供。

### 5.2 预测接口与视觉坐标

```text
future_object_position = predictor(video_history, table_imu_history)
```

起步可采用约 0.4 秒历史，以及 0.1 / 0.2 / 0.4 秒预测时距，作为待验证的实验配置。按时间戳截取历史，不能仅凭数组长度假定两种模态对齐。

优先使用已有的世界固定外部相机，预测该相机中的连续二维物体位置。腕部相机带来的视角运动留待需要时再扩展，第一版训练接口不依赖它。

标签固定采用物体上的同一参考点，记录视野内、遮挡等有效性信息。相机矩阵可以复用 [camera_utils.py](../robosuite/utils/camera_utils.py)，但现有投影函数会取整、交换行列并裁剪到图像边缘，不能直接用于连续位置标签。新标签路径保留浮点坐标，单独判断出界，并验证 RGB 翻转、坐标顺序与图像大小一致。

### 5.3 时间与输入隔离

- 输入只能包含决策时刻已到达的数据，保留 IMU 采样时间与交付时间。
- 视频、IMU、标签与动作使用同一仿真时钟。
- reset 后清空缓存；历史不足时使用有效性标记或跳过样本，不能伪造已采集历史。
- 物体真值只用于监督标签、评估和明确隔离的采集专家，不进入学习模型输入。
- 模式、seed、未来波形及实际支撑真值属于运行或评估信息，不自动传给预测器。
- 输入、未来标签和运行元数据在数据格式中明确分开，policy wrapper 只读取输入和模型预测。
- 按完整 episode、激励 seed 和模式划分数据集，避免重叠视频窗口跨训练、验证与测试集合。

模型输入不包含未来动作，因此接触、抓取和释放后的未来位置存在动作带来的不确定性。先用无接触片段验证 IMU 的预测增益，再覆盖操作过程并按接触阶段评估。动作可以进入采集日志和分析，但不因此改变已约定的模型输入。

## 6. 预测先验与 policy 接入

仓库目前以仿真、oracle 和验证工具为主，尚未发现可直接复用的视频世界模型训练实现。迁移先完成数据与接口，模型训练放在独立模块，不将整个训练框架引入环境代码。

统一先验格式：

```text
future_object_uv     [预测时距数, 2]
prediction_horizons  [预测时距数]
prediction_validity
prediction_time
```

一个 wrapper 负责历史输入、调用预测器和输出先验。下游 policy 在自己的输入编码层接收它：向量策略使用坐标编码，视觉策略可使用轨迹标记或热图。仅增加 observation 字典字段不足以让已有 policy 使用先验。

第一阶段训练预测器后冻结，再辅助 policy 学习。policy 训练和评测均使用模型预测的先验，真值未来位置只用于单独标记的参考实验。

| 对照 | 验证目的 |
|---|---|
| 视频预测 vs 视频 + IMU 预测 | IMU 是否改善未来位置预测 |
| 原 policy vs 视觉预测先验 vs 视觉 + IMU 预测先验 | 下游收益是否来自 IMU 提供的预测增益 |
| policy 直接接收 IMU | 区分预测模块的作用与单纯增加模态 |
| 未见模式、未见 Gamma | 分别验证模式泛化与强度泛化 |

固定相机、动作频率、历史长度、训练预算和执行延迟，记录预测器实际推理耗时。位置预测评估按预测时距报告误差和有效样本比例；policy 评估复用当前任务成功语义，并分别报告模式与 Gamma 条件下的结果。

当前主要任务逻辑位于 `vibration_pick_place_can.py`，`vibration_pick_place.py` 是薄封装。实施时先确定唯一当前公开入口为 `VibrationPickPlace`，合并仍需的实现，删除为旧 Can 环境兼容而存在的入口和字段转换。通用计算模块中仍使用的内部函数不因名称年代而复制一套，按需要直接更新调用者。

### 7.3 当前配置与完整性校验

当前物理加载与若干发布文件、旧 authority 和 hash 链耦合。删除历史资产之前应完成：

1. 将仍使用的甲板、隔振器、接触、控制频率和时间步长参数保存为唯一当前物理配置。
2. 将当前几何、传感器、激励模式定义、数据合同和运行参数绑定到当前 manifest；保持配置身份和数据完整性校验。
3. 修改物理加载、场景审计、状态生成、运行记录与 verifier，使其只依赖当前配置和当前 manifest。
4. 删除旧 runtime contract、旧阶段协议和 authority 链中的已替代文件，移除对应 imports、注册项和包内资源引用。
5. 新实验在完成当前验收前标记为未认证，不能从旧文件继承 PASS 或 scoreable 资格，也不能通过单纯重算 hash 声称实验已通过。

现有非 canonical 几何会进入旧 direct-mount 资格判断，该分支应整体替换为当前设计的验收逻辑，不能为新配置保留旧资格兜底。

不再维护旧文件读取器、旧字段自动迁移或历史结果重放入口。版本与 hash 仅用于标识当前合同、拒绝不兼容输入，不要求运行时支持已删除版本。

### 7.4 GPU 路径

[shakebench_mjwarp.py](../robosuite/utils/shakebench_mjwarp.py) 的 IMU 采样当前硬编码读取机械臂基座。先完成 CPU 路径；如果本轮不迁移 GPU，就删除旧 ShakeBench GPU 采集入口、专属脚本、核函数和过期说明，不保留一个只拒绝新配置的历史后端。

若决定同时保留 GPU 功能，则必须改成从当前传感器绑定解析工作台 body，迁移观测与记录格式，并通过 CPU/GPU 一致性检查后才能交付。仍被其他当前功能使用的通用 GPU 能力不属于待删除历史路径。

## 9. 实施顺序与验收

| 阶段 | 交付内容 | 验收条件 |
|---|---|---|
| A：收敛当前配置与依赖 | 唯一任务入口、当前参数与 manifest 结构 | 当前环境可构造；不依赖已经替代的历史 authority 链 |
| B：场景迁移 | 岸边实体地基、世界固定无机座机械臂、拓扑与间隙审计 | 振动时基座世界位姿恒定；工作台仍运动；抓放位置可达 |
| C：桌下 IMU | 唯一传感器、外参、时间戳、新字段 | 测量匹配工作台安装点运动；reset、延迟和噪声行为正确 |
| D：模式接口 | mode × Gamma、统一标定、运行身份 | 同配置可重放；Gamma 改变强度而不改变频率和相位；零强度无激励 |
| E：预测数据 | RGB/IMU 历史、未来位置标签、split | 时间对齐、标签投影正确、无真值或未来输入泄漏 |
| F：policy 接入 | 一个预测器接口和一个策略适配 | 先验证预测增益，再验证下游收益和延迟影响 |
| G：彻底清理与交付 | 删除历史代码、资产、输出及实施文档，修复引用 | 无历史兼容入口、失效命令、断链 imports 或指向已删除文件的当前说明 |

删除在相应功能迁移完成后随模块执行，阶段 G 用于最终核对，不用于留下长期双轨版本。

测试应围绕当前不变量定向更新：基座固定、桌下安装点的运动测量、Gamma 标定与模式可重放、视觉位置标签、输入隔离、当前配置完整性以及任务成功判定。重新验证三物体 × 两表面下的静态和代表性振动条件，不将旧测试改名后直接视为新设计证据。

最终交付包括可运行的当前环境、最新配置与数据合同、一个可用的数据采集入口、预测与 policy 连接接口、当前验收结果，以及仅描述最新设计的项目文档。历史实现和过时实施文档不在最终工作区中保留。
